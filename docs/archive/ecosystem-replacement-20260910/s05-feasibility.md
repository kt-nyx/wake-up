# S05 feasibility: reuse completed XML patches

> Dated evidence: identities, results and pending steps below describe this report's original checkpoint. For the combined offline candidate and superseding decisions, see [current state](../../current-state.md), [current scope](retained-features.md) and [R5](r5-combined-offline-review.md). Historical live results do not qualify the new package.

**Research checkpoint accepted by the parent steward — 9 September 2026. Replay is not implemented or live qualified.**

There is a plausible narrow way to reuse completed patch work: let RimWorld load its inputs normally, then substitute a previously completed patch result immediately before inheritance and definition creation. This can preserve ordinary failure recovery and callbacks. However, **existing evidence does not yet demonstrate a useful saving on a workload this conservative design would admit**. An observed XML-expanded workload contains custom operations and would refuse whole-document replay; the latest mixed workload also lacks complete admission evidence. Native-operation counts alone do not establish useful coverage.

Recommendation for steward consideration: continue S04's independent parsed-input work with the ownership requirements below, and retain S05 as a bounded implementation prospect once an eligible workload has a worthwhile patch cost. Do not broaden replay to arbitrary mod code to make the measured heavy lists qualify. This report neither accepts nor rejects roadmap scope.

## Native flow and proposed restore point

The inspected [LoadAllActiveMods](../../../artifacts/s05-feasibility/LoadedModManager.cs:26) performs, in order:

1. Clear inheritance state; initialize mods, load content and construct mod classes.
2. Load definition XML and combine **all** selected mods' inputs into one document, recording source assets against imported top-level nodes.
3. Clear/parse translation keys (`TKeySystem`), then load/check patch objects through `ErrorCheckPatches`.
4. Apply patches in mod/operation order.
5. Register/resolve inheritance, convert XML into definition objects, apply native dependency filtering and assign source ownership.
6. Call each top-level patch's `Complete`, clear patch caches, then clear inheritance state.

The proposed first boundary is **the `ApplyPatches(xmlDocument, assetlookup)` callsite in `LoadAllActiveMods`, after error checking and before `ParseAndProcessXML`**. A later implementation would keep steps 1–3 and 5–6 running. At step 4 it could select either the ordinary call or a completely staged patched document, source map and patch-instance state. Capture the pre-inheritance result at the corresponding exit on an ordinary successful load. Do not cache constructed Def objects.

This is deliberately a *late* restore: it saves patch execution, not source reading, XML parsing, combination or patch-object construction. Those costs remain in the comparison. Moving the hit before `LoadModXML` would require a separate complete input/callback/TKey reconstruction contract; a file-existence check followed by late decoding is unsafe. The source-established boundary is not yet an implemented transaction: simply changing an argument inside a normal `ApplyPatches` prefix would not update both caller locals used afterward. S05 must verify the actual callsite and publish both references together through a small, reviewed integration.

There is an important translation detail. On this exact reference, [ShouldUseHardcodedMapping](../../../artifacts/s05-feasibility/TKeySystem.cs:46) returns true and [ParseDefNode](../../../artifacts/s05-feasibility/TKeySystem.cs:224) immediately returns. Preserve the native clear/parse/build lifecycle and admit only that verified behavior initially. The alternative code retains references to pre-patch nodes; swapping documents would require remapping those references, including removed nodes. A modified mapping path or foreign hook must refuse this restore, not silently parse the patched document instead.

## Which operations qualify

Eligibility means an **exact runtime type and reviewed effective implementation**, not a class-name prefix, mod allowlist or assumption that native-looking XML is safe. Review the complete operation tree, including unselected branches. Subclasses and any unknown nested operation refuse the initial whole load.

| Candidate native operations | Dependencies and state |
|---|---|
| Add, AddModExtension, Insert, Remove, Replace, SetName | Current complete XML tree, XPath and serialized operation fields/value nodes. They select/mutate XML; AddModExtension imports XML and does not instantiate extension code here. |
| AttributeAdd, AttributeRemove, AttributeSet, Test | Current XML, XPath, attribute/value fields and the common success mode. |
| Sequence and Conditional | All children must qualify. Preserve sequence short-circuiting and selected branch outcomes through recorded instance state. |
| FindMod | Additionally depends on active **display names**, not just package IDs: [HasActiveModWithName](../../../artifacts/s05-feasibility/ModLister.cs:199) compares `mod.Active && mod.Name == name`. Include exact names/active state and this method's behavior. |
| Base PatchOperation, arbitrary subclasses or changed methods | Ordinary execution. The base worker logs an error. No automatic code-purity analyzer or inferred contract for custom code. |

The [native extracts](../../../artifacts/s05-feasibility/PatchOperationAdd.cs) cover all 13 concrete worker types above (Conditional is counted once), their base classes and lifecycle. They establish a finite reviewable family, not runtime admission today. Existing Wake-Up [XML search integration](../../../src/WakeUp/XmlSearch/DefLookupRuntime.cs:68) covers 11 query workers; that narrower query substitution does **not** authorize skipping their surrounding calls.

Hashing a custom assembly or its settings cannot prove its operations safe to skip: unchanged code may read randomness, clocks or external files, register callbacks or mutate other state. Such operations run normally. A future explicit dependency/effect contract is separate work.

## Inputs, attribution and recovery

Every hit needs the following checks; the initial late boundary can obtain actual loaded inputs without inventing another discovery pipeline.

- Bind **all selected definition inputs**, including later mods, and all ordered patch inputs. Retain exact selected source/package identities, full content digests, effective load folders, override winners, added/deleted files and actual order. [DirectXmlLoader](../../../artifacts/s05-feasibility/DirectXmlLoader.cs:17) selects first folder winners and imports results in indexed order; a fresh alphabetical sort is not an equivalent contract. Paths, timestamps and sizes alone are insufficient. Hash bytes from the same read snapshot used to parse; if that cannot be established, refuse until S04 provides it. Also bind the actual combined input tree and instantiated operation fields at the late boundary, so earlier transformations cannot be hidden by unchanged disk bytes.
- Include format/algorithm version, parsing/XML-library behavior, relevant game methods and participating code identities, effective settings/command-line modes, active package order and FindMod names. Bind effective code after Prepatcher changes as well as relevant Harmony hooks; a matching disk DLL or empty Harmony owner list alone is insufficient. Recheck at use. This is per-feature admission, not reinstating a blanket whole-game version restriction. Unknown virtual/archive sources or unsupported transformations keep ordinary loading.
- Preserve tree structure and node order, names/namespaces, attributes, text and observable node kinds. Do not silently normalize beyond native behavior. Native file parsing ignores comments/whitespace using specific reader settings, but generated patch values can still make node details observable; see [LoadableXmlAsset](../../../artifacts/s05-feasibility/LoadableXmlAsset.cs:20).
- Store source attribution separately from XML. Map restored nodes back to **this launch's real source assets**, including exact filenames/folders and the distinction between mapped and unmapped nodes. Native [ApplyPatches](../../../artifacts/s05-feasibility/LoadedModManager.cs:289) does not update `assetlookup`: a newly added or replaced root can be unmapped, while a mutated original root retains its source. Do not assign every patch-created node to the patch's mod or invent one `cached` asset per package. Removed map keys/detached nodes must also be represented if preserving the complete dictionary; otherwise demonstrate that the admitted consumer cannot observe them before narrowing the format. Native `AddDef` sets both `modContentPack` and `fileName`.
- Keep `MayRequire`, `MayRequireAnyOf`, abstract/template handling and inheritance in the original subsequent stage. Do not prefilter the cached document. [XmlInheritance](../../../artifacts/s05-feasibility/XmlInheritance.cs:77) maintains node-keyed global state and chooses parents using mod ownership; this is a separate problem from saving a patched tree.

Stage and validate the complete bounded payload, current asset bindings and patch-state bindings **privately**, while the untouched ordinary document/map remain available. Commit must consist only of prevalidated state/reference assignments on the owning loading thread, without allocations, virtual calls or partially clearing live collections. If that cannot be guaranteed, retain ordinary execution and redesign the boundary. A failed read, hash, decode, binding or capacity check must call ordinary patching exactly once on the original inputs. Never catch a partial restore and patch it again. Cache-writing failure leaves the already computed native result intact.

Use S01's `CacheLaunchPolicy` and a distinct versioned `OwnedCacheStore` category, with bounded entries/memory and capacity admission before expensive capture. Register central clear/completion participation. Its payload integrity and atomic file publication do not themselves make the multi-object game-state commit safe. No XML size/quota value is selected by this research.

## Diagnostics, callbacks and competing loaders

[PatchOperation.Apply](../../../artifacts/s05-feasibility/PatchOperation.cs:24) applies the success mode and changes `neverSucceeded`. [Sequence](../../../artifacts/s05-feasibility/PatchOperationSequence.cs:10) also retains `lastFailedOperation`; short-circuited/unselected children retain their prior state. A cached document without these values can emit false failures later. Record the full reviewed operation-tree state, including references by operation position, and restore it to the normally constructed instances. Preserve native `Complete` calls **once, after definition conversion**, and native cache clearing. Do not call completion early or fabricate success for every operation.

For the first version, refuse generation publication when parsing/configuration/patch execution reports an error, a worker throws, or a top-level operation would emit a completion failure. Legitimate inverted tests and unused children are not themselves errors. Keep native earlier diagnostics on every launch; non-cacheable failures execute normally. This avoids reproducing exception logs or inventing a diagnostic replay system. Any ordinary callback failure after a successful hit follows the native path; it is not permission to rerun already published patches. Profiling should report cache validation/restoration separately rather than claim the skipped workers ran.

Admission must cover skipped worker/base methods and the surrounding lifecycle, including relevant hooks that observe XML or hold document/map aliases. Unknown callbacks or a supplier owning a competing combined-document cache refuse replay; their ordinary execution remains. Gagarin assistance and S04 must have one owner for any reused input. Loading Progress can rewrite loading flow and patch iteration, so the native callsite is not presumed reachable or equivalent under it. Its [source](../../../artifacts/ecosystem-review-20260909/sources/loading-progress/Source/ilyvion.LoadingProgress/StartupImpact/Patches/LoadedModManager_ApplyPatches_Patches.cs) and the [rejected Gagarin bridge record](../five-loading-opportunities.md) require an explicit future coexistence decision, not a name-based exception. Prepatcher remains required.

For an admitted load, the estimate is `saved patch time minus validation, restoration and state-binding overhead`; all source-loading costs remain. Even eliminating the entire 9.96 s stage could not save more than that stage in that observation, and that workload is not admitted. Do not transfer its budget to a different all-native list, equate the native call fraction with coverage, or add the existing XML-search saving to work replay would skip. First capture costs and invalidation frequency also affect whether repeated launches repay construction. Native replay has no measured success yet, and retaining source validation makes overhead a real stopping risk.

## Handoff and remaining decision

S04 should supply same-snapshot input identity, actual selected order, real asset attribution and fresh independently mutable documents. It can ship alone, and a slower parsed-cache encoding need not block late S05 replay. Initial S05 should retain whole-load refusal and ordinary inheritance. Prefix/run checkpoints are not recommended here: all definition inputs would still need validation, and unknown operations can retain aliases or produce state outside XML. A later proposal must show both a meaningful eligible interval and a safe state boundary.

Before costly S05 implementation, the steward needs a useful **admitted** workload and a concrete treatment of the effective loading hooks. A narrowly scoped future implementation would then need node/source/state equivalence, callback ordering, changed-input/setting/code/order/folder refusal, malformed payload recovery and one authorized matched forward/reverse comparison including full overhead. No new harness or general analyzer is justified by this report. Resolved inheritance reuse remains a later S05 checkpoint: no isolated material merge saving or complete restoration contract is established here.

Only this report and the S05 ledger changed. Validation is limited to source/reference inspection, existing evidence review, document links and Git scope/whitespace checks. No runtime edit, prototype, build, new test harness, package, deployment or live run occurred; normal game data, Deck, security settings and publication were untouched. On-demand remains optional/off by default; native-helper bundling remains unresolved. **Checkout ownership returns to the steward at this report commit. This task stops after handoff.**
